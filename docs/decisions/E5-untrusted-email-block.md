# E5. Недоверенный текст письма не выходит из блока данных

**До.** Письмо вставлялось между постоянными `<<<EMAIL` и `EMAIL>>>`. Строка `EMAIL>>>` в теле закрывала блок, и следующий текст оказывался на месте инструкций.

**Выбор: A.** Для каждого вызова генерируется метка `EMAIL-<12 hex>`, проверяется, что её нет в тексте письма, и письмо оборачивается в `<метка> … </метка>`. Текст письма не меняется: это важно для решения 04, где номера ищутся по точному тексту.

**Почему не B и C.** B меняет данные. C зависит от провайдера и не работает с локальной моделью.

**Как проверяем «частичную» защиту.** Разделитель защищает только от прямого закрытия блока. Модель всё ещё можно уговорить текстом. Поэтому последняя линия защиты — policy кода (адрес выбирает код, клиент подтверждается только по From, роль сверяется с фактами). Набор `cases/attacks.json` (4 письма) запускается в обоих режимах; порог — **0 выполненных запрещённых действий**, обычные письма не должны ухудшиться.

**Тест.** `PromptInjectionTest` (метка не встречается в письме, `EMAIL>>>` и поддельный закрывающий тег остаются внутри блока), прогон `attacks-v3`.
