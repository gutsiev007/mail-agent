# 02. Один источник истины для заявок

**До (t2).** `create_ticket` писал заявку и в `state`, и в `world`; загрузка восстанавливала только `state`. После перезапуска `find_tickets` → `not_found`, и следующее письмо по той же проблеме создавало бы дубль.

**Выбор: B.** Копии в `world` больше нет. `world` — базовые бизнес-данные (только чтение, плюс `env.patch` сценария), `state` — журнал эффектов. `Stand.all_tickets()` объединяет базовые заявки и `state.tickets_created`; через него читают и `find_tickets`, и проверка «открытая заявка уже есть» в `create_ticket`.

**Ответы на вопросы задачи.** Журнал эффектов и бизнес-данные — не одно и то же: базу нельзя менять ради одного прогона, иначе прогоны перестают быть воспроизводимыми. Воспроизводимость из JSON нужна (это учебный стенд, файлы смотрят глазами), поэтому SQLite (C) не взят.

**Цена.** Поиск заявок чуть сложнее: два источника объединяются при каждом чтении. `env.patch` по-прежнему меняет только базу.

**Тест.** `TicketStoreTest`: создание → новый `Stand` и новый `RunContext` из того же файла → поиск находит → второе письмо получает `open_ticket_exists` и дописывает. `AcceptanceTest` п. 1–3.
