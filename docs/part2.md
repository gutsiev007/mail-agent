# Часть 2. Трассировка и регулярные проверки

## Шаг 7. Трасса

- Формат: JSONL, один файл на запуск набора — `runs/<batch>/trace.jsonl`; одинаковый для агента и workflow.
- `run_id` = `<batch>-<mode>-<case_id>-try<N>`: три повтора письма → три `run_id`, общий `case_id`.
- В каждой записи: `run_id`, `case_id`, `mode`, `event_index`, `event_type`, `prompt_version`, `tools_version`, `code_version` (хеш кода), `dataset_version` (хеш данных и кейсов). Модели и роли — в `run_start` и в каждом `llm_call` (`role`, `model`), полная конфигурация — `runs/<batch>/meta.json`.
- События: `run_start` → `llm_call` (токены, длительность, предложенные вызовы) → `tool_call` / `tool_result` (связаны `call_id`, время начала и конца, число повторов) → `decision` / `extraction` → `error` (если было) → `run_end` (эффекты стенда, заблокированные попытки, оценка).
- Ключи API в трассу не пишутся (заголовки не логируются).

```bash
python -m mailagent show dev-p1-agent-mail-07-try2      # все события попытки
python -m mailagent effects dev-p1-agent-mail-07-try2   # фактическое состояние стенда
```

**Как искать первый неверный шаг:** идти по событиям сверху и сравнивать с ожиданием кейса. Пример различения причин: если `tool_result` вернул `not_shipped`, а следующим `llm_call` модель предложила `logistics` — это решение модели (policy вернёт `blocked: rule_mismatch`); если модель предложила `order_operations`, а эффект ушёл на другой адрес — ошибка исполнения в коде.

## Шаг 8. Регулярные проверки

- Набор: `cases/dev.json` (+ `cases/new.json` после первого разбора), найденные ошибки добавляются кейсами в `cases/regression.json` (старые версии не удаляются; при смене правил — новый кейс с суффиксом `-v2` и пояснением в `note`).
- Проверки в кейсе записаны до запуска: `expected.any_of` (допустимые наборы эффектов — траектория не сравнивается), `forbidden` (запрещённые эффекты). Агент их не видит: проверяет `grader.py` по состоянию стенда.
- Проверки бизнес-правил сделаны кодом (policy + grader): маршрут по статусу заказа/договора, отсутствие второй заявки, нет внешних адресатов. Смысл обещаний в `note` не оценивается — LLM-оценщик **не использовался**.
- Одна команда — набор, трассы, таблица:

```bash
python -m mailagent run --mode both --set dev,regression --trials 3 --prompt p2 --batch reg-p2
python -m mailagent compare reg-p1 reg-p2 --mode agent
```

`compare` пишет таблицу «до/после» по всем метрикам и списки кейсов, которые исправились и сломались.

### Практика шага 7: первый неверный шаг
`python -m mailagent show dev-p2-agent-mail-11-try1`: событие `tool_result` после `create_ticket` с `basis` без `contract_id`. Инструмент ответил `contract_not_observed`, хотя D-11 уже был получен. Дальше модель повторяет чтение и сдаётся. Причина в тексте ответа инструмента, а не в данных или исполнении. Выбранное изменение — t2 (см. `prompts/CHANGES.md`).

Workflow, новые письма (`compare new-final new-v2 --mode workflow`): 9/15 → 15/15, исправились new-01, new-02 (подстановка номера заказа кодом, wf2).

**Какая метрика изменила моё решение и почему:** ложные пересылки и заявки. Правильных ответов у агента стало больше, но ложных действий тоже (1 → 11). Ошибку «не туда» policy не ловит, а передачу человеку видно сразу. Поэтому изменение t2 я оставляю: оно убирает ложные отказы агента (20 → 4). А агента как основной режим не выбираю (см. `docs/results.md`).

### LLM-оценщик
Не использовался. Все проверки программные: эффект на стенде и запрещённые действия (`grader.py`), бизнес-правила (policy в `tools.py`).
