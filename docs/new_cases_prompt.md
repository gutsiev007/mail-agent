# Промпт для новых проверочных писем (шаг 6)

Новые письма (`cases/new.json`, 5 шт.) составлены отдельным ИИ-агентом, которому передан только текст ниже — без кода и промпта агента. До финального прогона они не использовались для настройки.

---

Составь 5 проверочных писем для системы маршрутизации входящей почты сервисной компании. Верни только JSON-массив.

**Правила компании:**
- Технические обращения по действующему расширенному договору получает группа инженеров из договора; по действующему обычному — общая поддержка.
- Если обслуживание закончилось, обещать его нельзя: письмо передают ответственному за договор.
- Оплаченный, но не отгруженный заказ — обработка заказов; после отгрузки — логистика.
- Продолжение открытого обращения добавляется в эту заявку (исполнитель уведомляется); вторую заявку не создавать.
- Если клиента или предмет нельзя определить однозначно — уточнить у отправителя или передать сотруднику.
- Новые покупки — отдел продаж. Отправитель подтверждается только точным email контакта клиента.

**Данные стенда:**
- Клиенты: C-11 «Вектор Север» (anna@vektor-sever.test), C-12 «Вектор Сервис» (anna@vektor-servis.test), C-21 «Орион» (oleg@orion.test), C-31 «Маяк» (irina@mayak.test).
- Договоры: D-11 (C-11, расширенный, действует, группа «Север»), D-12 (C-12, обычный, закончился, ответственная Марина), D-21 (C-21, обычный, действует). У C-31 договора нет.
- Заказы: O-51 (C-11, оплачен, передан перевозчику), O-52 (C-21, оплачен, не отгружен).
- Обращения: T-9 (C-31, открыто, исполнитель Сергей, тема «Сбой печати этикеток на линии 2»).
- В письме можно изменить один факт стенда через `env.patch` (например `"orders.O-51.shipping_status": "not_shipped"`, `"contracts.D-21.service_status": "expired"`) или включить сбой источника `env.faults` (`{"get_order": "unavailable"}`; источники: find_customer, get_contracts, get_order, find_tickets, read_thread).

**Возможные итоговые действия** (поле `expected.any_of` — список допустимых наборов действий):
- `{"type":"forward","role":"order_operations|logistics|sales|contract_manager","ref":"O-xx или D-xx (для sales не указывать)"}`
- `{"type":"create_ticket","role":"engineers_group|support_general","ref":"D-xx"}`
- `{"type":"append_ticket","ticket_id":"T-xx"}`
- `{"type":"clarification"}` — вопрос отправителю
- `{"type":"escalate"}` — передать сотруднику

**Формат одного письма:**
```json
{"case_id": "new-01", "path": "краткое имя пути обработки",
 "note": "почему ожидается такой итог",
 "env": {},
 "email": {"message_id": "new-01", "from": "адрес", "from_name": "имя", "subject": "тема", "body": "текст"},
 "expected": {"any_of": [[{"type": "forward", "role": "logistics", "ref": "O-51"}]]},
 "forbidden": [{"type": "forward", "role": "order_operations"}]}
```

Требования: письма естественные и разнообразные по формулировкам; не меньше 3 разных путей; хотя бы одно письмо с двумя запросами, одно с неоднозначным отправителем или предметом и одно с изменённым фактом стенда. `message_id` совпадает с `case_id`.
